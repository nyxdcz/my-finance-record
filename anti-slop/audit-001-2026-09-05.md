## Findings

### F-001 - High - Em dash characters are shipped in visible UI copy

- Rule: R-02 (hard gate; no em dashes in UI text outside documentation).
- Page/path and viewport: Dashboard Cash Flow and Overview, Finance, Work, Insights, Settings, and dialogs at all tested live widths; the fallback is visible at the compact live viewport and is present in the desktop render paths.
- Steps to reproduce:
  1. Open `?page=dashboard`.
  2. Select Cash Flow.
  3. In Savings trend, observe the Change percentage fallback rendered as `—` when no baseline exists.
  4. Open settings or a form that exposes project compensation, planning help, cloud status, or account previews; observe additional `—` placeholders and prose separators.
- Expected: Use an explicit phrase such as `No saved baseline`, `Not available`, or a permitted separator such as a middle dot.
- Actual: Runtime strings contain U+2014 em dashes in placeholders, helper text, sync toasts, and generated labels. Representative locations are `index.html:1148,1467,1572,2372,4070,4433`, `assets/js/reports-insights.js:447`, `assets/js/cloud-sync.js:668,739`, `assets/js/account-ledger.js:1137-1474`, and `assets/js/household-splits.js:595`.
- Root cause: The source uses the em dash both as a fallback value and as prose punctuation; there is no copy lint or normalization rule for UI strings.
- Files changed: `index.html`; canonical runtime sources `assets/js/account-ledger.js`, `assets/js/cloud-sync-lifecycle.js`, `assets/js/cloud-sync.js`, `assets/js/household-splits.js`, `assets/js/import-center.js`, and `assets/js/reports-insights.js`; generated source copies `household-splits.js` and `import-center.js`; regression harness `tests/run.mjs` and `tests/regression/validate-ui-copy.mjs`.
- Fix implemented: Replaced user-facing U+2014 fallback values with explicit `N/A` or `Not signed in` states and changed prose separators to a colon or sentence boundary. Input normalization regexes and calendar ICS export labels remain unchanged because they are not rendered UI copy.
- Test coverage / verification evidence: `node tests/regression/validate-ui-copy.mjs` passed; `npm run lint` passed; `npm run test:regression` passed all 21 suites, including the new copy guard. The guard scans canonical UI sources and permits only the two intentional ICS export labels.
- Screenshot links or paths: No new local screenshot artifact; the browser screenshot runner was blocked by the Chromium sandbox error described above.

### F-002 - High - Realistic finance records are seeded without an in-context sample label

- Rules: R-17 (no invented numbers or metrics presented as proof) and R-38 (use real content or honest placeholder content).
- Page/path and viewport: `?page=dashboard`, `?page=money`, `?page=projects`, `?page=payments`, and `?page=reports`; reproduced in the live app at its compact viewport and applicable to desktop, tablet, and mobile layouts.
- Steps to reproduce:
  1. Open the public app in a fresh browser profile, or clear only the app's local storage in a disposable test profile.
  2. Visit Dashboard or Finance.
  3. Observe realistic account balances such as Cash `4,000` and Maya `5,265`, recurring expenses such as Apple Music `219`, Rent `3,500`, and Home Credit `4,159`, and named projects with balances.
  4. Check the surrounding page chrome: the records are presented as normal active finances; no Dashboard or Finance banner identifies them as sample or demo records. The sample explanation appears only in Settings reset UI.
- Expected: Start with an empty state, or clearly label seeded records as sample/demo data at the point where they are shown, with a safe way to switch to user data.
- Actual: A first-run user can reasonably read the seeded values, dates, names, payment rates, and trend metrics as their own records. The live app accessibility tree exposed these values as ordinary finance content.
- Root cause: `createSampleData()` in `index.html:1799-1849` returns realistic accounts, expenses, projects, dates, and amounts. `normalizeData()` falls back to that data at `index.html:2089-2091` when saved data is absent. There is no in-context sample-data indicator on the Dashboard, Finance, Work, or Insights surfaces.
- Files changed: `index.html`, `assets/css/app.css`, `tests/run.mjs`, and `tests/regression/validate-sample-data-disclosure.mjs`.
- Fix implemented: Fresh first-run fallback data is tagged in a local-only sample-state key and exposed through a persistent banner across app sections. The banner offers a confirmed “Start with empty workspace” action that creates a recovery snapshot, replaces only the active local data with schema-compatible empty data, and records an undo entry. Backup, sync, and legacy restores clear the sample marker; the existing explicit sample reset re-enables it.
- Test coverage / verification evidence: `node tests/regression/validate-sample-data-disclosure.mjs` passed; `npm run test:regression` passed all 21 suites after runtime preparation; `npm run lint`, `npm run inspect`, and `npm run maintainability` passed. No real finance records or cloud data were touched.
- Screenshot links or paths: No new local screenshot artifact; live CUA inspection supplied the visual/accessibility evidence.

### F-003 - Medium - Liquid Glass is applied across too many UI layers

- Rule: R-10 (glassmorphism is capped at one or two purposeful elements and must not cover navbar, cards, modals, and sidebar simultaneously).
- Page/path and viewport: Shared app shell on Dashboard, Finance, Work, Insights, and Settings at desktop and compact live viewports.
- Steps to reproduce:
  1. Open any primary route.
  2. Inspect the top bar, sidebar, workspace switcher, weekly marquee/day cards, a popover, and a dialog header or footer.
  3. Observe that multiple layers use translucent gradients, inset shadows, and backdrop blur at the same time.
- Expected: Reserve the material for one or two clearly purposeful floating surfaces; keep navigation and data surfaces visually stable and opaque.
- Actual: The shared stylesheet applies `backdrop-filter` to the top bar (`liquid-glass.css:33-38`), sidebar (`114-120`), workspace controls and marquees (`42-54`, `155-172`), popovers (`178-185`), modal chrome (`195-203`), and toasts (`209-215`). The marquee's generated day/event cards also receive the material. This is a page-wide treatment rather than a limited accent.
- Root cause: Broad `:is(...)` selectors and shared Liquid Glass variables are loaded globally. The deployed root stylesheet and `assets/css/liquid-glass.css` carry the same scope, so every route inherits it.
- Files changed: `assets/css/liquid-glass.css`, generated runtime `liquid-glass.css`, `tests/run.mjs`, and `tests/regression/validate-liquid-glass-budget.mjs`.
- Fix implemented: Added a final material-budget override that makes navigation, workspace tabs, marquees, repeated day cards, menus, dialog chrome, and toasts opaque with no blur. The cloud-status popover remains the single purposeful glass surface. Reduced-transparency and forced-colors modes still disable its blur.
- Test coverage / verification evidence: `node tests/regression/validate-liquid-glass-budget.mjs` passed; `npm run test:regression` passed all 21 suites. Existing browser tests still cover the root runtime stylesheet, and the generated root copy is kept in sync for local/browser delivery.
- Screenshot links or paths: No new local screenshot artifact; live CUA screenshot and accessibility inspection were performed, but the Playwright capture suite could not launch Chromium in this sandbox.

### F-004 - Medium - Compact form focus treatment is too faint for keyboard users

- Rules: R-25 (WCAG non-text focus contrast target of at least 3:1) and R-32 (keyboard reachability with a visible focus indicator).
- Page/path and viewport: Finance filters and form controls on `?page=money`, plus shared inputs and icon triggers in Settings and dialogs; especially compact desktop and mobile layouts.
- Steps to reproduce:
  1. Open Finance and place focus in the expense search field, category selector, or More filters control using Tab.
  2. Continue through the compact income toolbar or a record icon trigger.
  3. Observe the focus treatment at normal and dark/light themes.
- Expected: A persistent 2-3px focus ring or equivalent boundary that remains clearly visible against both themes and reaches at least 3:1 non-text contrast.
- Actual: Several selectors remove the outline, make the border transparent, and substitute a 1px inset `color-mix` ring at only 18-20% primary opacity. Relevant rules are `assets/css/app.css:3037-3042`, `3120`, `3224-3227`, `5235`, plus the base outline resets at `242` and `888-898`. A 70% primary ring (`#356FD1` on white, 4.83:1) passes, but the approximately 18% blended ring is about 1.3:1 on white and fails the 3:1 non-text target.
- Root cause: Later compact-toolbar overrides use `outline:none !important`, `border-color:transparent`, and low-opacity inset shadows. The rule is shared by keyboard focus and pointer focus, so the keyboard state receives no stronger replacement.
- Files changed: `assets/css/app.css`, `tests/run.mjs`, and `tests/regression/validate-keyboard-focus.mjs`.
- Fix implemented: Added a final, theme-aware `:focus-visible` rule for compact expense, paid, project, and income filters, the month display control, and icon triggers. The rule uses a 2px outline plus a 1px boundary ring and preserves a red error-state ring.
- Test coverage / verification evidence: `node tests/regression/validate-keyboard-focus.mjs` passed; `npm run lint` and `npm run test:regression` passed. The full browser runner remains blocked by the Chromium Mach-port permission error described above.
- Screenshot links or paths: No new local screenshot artifact; browser screenshot capture was unavailable because Chromium could not obtain the sandbox Mach port.

### F-005 - Low - Visual direction is not documented in a DESIGN.md or equivalent brief

- Rules: R-31 and R-37 (purposeful visual direction and a documented design brief before UI decisions).
- Page/path and viewport: Repository-level; affects every route and breakpoint rather than one viewport.
- Steps to reproduce:
  1. Inspect the repository root and documentation folders for `DESIGN.md` or an equivalent current visual brief.
  2. Review the stylesheet ownership and comments; several files carry independent V14/V15/phase revisions, but no single source of truth defines the visual direction, material budget, typography scale, or breakpoint intent.
- Expected: Keep a short, current design brief that states the visual direction, material limits, radius hierarchy, typography, color semantics, and responsive rules used to judge new changes.
- Actual: No `DESIGN.md` exists. The app has useful token and CSS comments, but they are distributed across stylesheets and do not provide one auditable direction document.
- Root cause: Design decisions are encoded in implementation files without a canonical brief.
- Files changed: `DESIGN.md`, `tests/run.mjs`, and `tests/regression/validate-design-brief.mjs`.
- Fix implemented: Added a concise visual direction brief covering opaque data surfaces, the one-surface glass budget, radius hierarchy, typography and semantic colors, responsive behavior, touch targets, keyboard focus, and the review viewport checklist. This is documentation only and does not alter finance data or schema behavior.
- Test coverage / verification evidence: `node tests/regression/validate-design-brief.mjs` passed; `npm run inspect`, `npm run lint`, `npm run maintainability`, and `npm run test:regression` passed.
- Screenshot links or paths: Not applicable; this is a repository quality finding.

### F-006 - High - Desktop expense action footer divider cuts through card metadata (fixed)

- Rule: Layout integrity and action-row containment; the attached Finance screenshot is the reproduction evidence.
- Page/path and viewport: `?page=money`, Budget & Expenses, list mode, fine-pointer desktop at approximately 1440px wide; the same footer is rendered in the First half, Second half, and Other expenses period cards.
- Steps to reproduce (before the fix):
  1. Open Finance and select Budget & Expenses.
  2. Use list mode at a wide desktop viewport with expense records visible in all three period cards.
  3. Inspect the account, amount, and Mark paid/Edit action area at the bottom of a card.
  4. Observe a horizontal rule extending across the card and cutting through the metadata/action transition, as shown in the attached screenshot.
- Expected: The account and amount metadata remain readable, and the action footer stays inside the card with its controls below the metadata and no divider crossing the row.
- Actual before the fix: The action footer's horizontal border and bleed margins visually overlaid the account/amount row and could make the buttons appear detached from or clipped by the card.
- Root cause: The earlier desktop `.desktop-record-actions` rule in `assets/css/production-ui-audit.css` used `margin-top: 2px`, `padding-top: 8px`, `width: 100%`, and `border-top: 1px solid var(--line)`. The compact overlay in `assets/css/expense-compact.css` also used negative horizontal margins and a top border. Because the footer is a grid child spanning the card, those values made the rule bleed into the preceding metadata row.
- Files changed: `assets/css/expense-compact.css`, generated `production-ui-audit.css`, and `tests/browser/production-ui-audit.spec.mjs` (focused fix already present in the repository history).
- Fix implemented: Kept the desktop action bar inside the card content box with `margin: 4px 0 0`, `padding: 0 0 0 37px`, `width: auto`, and `border-top: 0`; preserved the grid span, button sizing, checkbox placement, and responsive phone rules.
- Test coverage / verification evidence: `tests/regression/validate-expense-divider.mjs` statically guards the compact source rule; `tests/browser/production-ui-audit.spec.mjs:282-311` asserts zero action-footer border width, in-card left/right bounds, and an action top at or below the account/amount metadata. The surrounding suite also covers all three period disclosures and phone disclosure sizing. Source inspection confirms the final runtime overlay carries the same `border-top: 0 !important` contract.
- Screenshot links or paths: Before image: `/Users/nyx/Desktop/Screenshot 2026-09-02 at 7.04.43 PM.png` (the user-provided attachment). No after image was emitted because the local Chromium runner could not obtain its Mach port; see the environment note below.
